# Вечерние замедления VPN: причина установлена (2026-06-11)

Расследование вечерних провалов скорости туннеля на основном роутере
(Cudy WBR3000UAX, `root@192.168.10.1`, линия <домашний провайдер>, WAN <WAN-IP>).
Все замеры сняты 2026-06-11 в 21:50–22:10 MSK, во время активного окна замедления.

## Вывод

**ТСПУ на аплинке домашнего провайдера (<домашний провайдер>) в вечерний пик полисирует
отдельные TCP-потоки к префиксам зарубежных хостеров до фиксированных
~60–90 КБ/с. Воздействие по-потоковое (per-flow), а не по-IP: каждое новое
TCP-соединение — лотерея, часть потоков проскакивает на полной скорости.**

- Сервера ни при чём (одновременные потоки к одному IP: один задушен, другой быстрый).
- Протокол ни при чём (настоящий TLS к dl.google.com душится так же, как VLESS —
  Reality/XHTTP не детектируется, ключ — IP назначения).
- Линия ни при чём (Selectel RU 13.5 МБ/с, cachefly до 24 МБ/с в ту же минуту).
- Модель «волны по IP» из наблюдений 06-09/06-10 — артефакт: одиночные замеры
  по-потоковой лотереи выглядят как «волны».

туннеля тут же вытягивает несчастливый билет и залипает (внешний поток XHTTP
один и живёт долго, перехэширования нет).

### 3. Главное доказательство: 6 повторных «сырых» TLS к одному IP (22:04)

Без VLESS: `curl --resolve dl.google.com:443:<server-PL>` — Reality-fallback
польского сервера проксирует чужой TLS на настоящий dl.google.com. Каждый запрос —
новое TCP-соединение:

```
Польша #1 :   72 KB/s
Польша #2 :   64 KB/s
Польша #3 :   82 KB/s
Польша #4 : 1558 KB/s   ← проскочил
Польша #5 :   62 KB/s
Польша #6 : 3893 KB/s   ← проскочил
США    #1 : 2341 KB/s
США    #2 : 2377 KB/s
```

Один IP, одна минута, одинаковые запросы — бимодальная лотерея по потокам.
Медленный режим прибит к узкому коридору ~60–90 КБ/с = настроенный полисер
(перегрузка дала бы шумный разброс). И это **настоящий** TLS к Google —
значит, ключ воздействия — IP назначения, а не сигнатура протокола.

### 4. Прочее

- Последовательные пробы через один инстанс xray (один внешний поток) — все
  медленные (93→58→27→38→48→50 КБ/с): несчастливый билет залипает на весь
  срок жизни соединения. Свежий инстанс = новый розыгрыш.
- ICMP RTT во время зажима безупречен (Польша 68 мс, Швеция 37 мс) — полисер
  душит полезную нагрузку, не задержку. Latency-пробы такое не видят
  (потому tput-guard и был нужен).
- Шансы «проскочить» в этот вечер: Швеция ≈0%, Польша ~30%, США 100%
  (маршрут через Hurricane Electric, видимо, обходит точку шейпинга, либо
  префикс не в списке; потолок США ~2.4 МБ/с — трансатлантика).
- Маршруты (traceroute): Швеция через RASCOM (AS20764) → Netnod;
  Польша и США через Hurricane Electric (184.104.x); ТСПУ-хопы молчат (`*`).

## Что из этого следует (бэклог, не реализовано)

1. **Re-dial вместо переключения**: при срабатывании tput-guard сначала
   передёрнуть соединение к *текущему* серверу (мягкий рестарт xray = новый
   внешний поток = новый билет лотереи), перемерить — и только если не помогло,
   бенчмаркать и переключаться. Дешёво, лечит и залипание туннеля, и
   20-минутные ямы кулдауна.
2. **XHTTP `xmux`** (несколько внешних соединений) — размазывает лотерею:
   один задушенный поток из N почти не влияет на суммарную скорость.
3. Замер tput в watchdog едет через **один** внешний поток (оба зеркала через
   один инстанс xray) — одиночный плохой билет читается как «сервер медленный».
   Мерить двумя независимыми свежими потоками и брать максимум.
4. Вечерний приоритет США-выхода как стабильного пути.
5. **Нидерланды (<server-NL>) мертвы на стороне сервера**: 0 КБ/с свежей
   пробой, TLS handshake не проходит (5/5 ошибок в ночь 10→11.06). Чинить/убирать
   на панели.
